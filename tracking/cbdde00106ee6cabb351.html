回访更正：LiteLLM 事故的入口是未撤销的公开管理密钥

按时间保留当时的判断和后续核查；历史收录不代表刚刚重新验证。

2026-11-07 · 当时的记录

10 月 23 日的报道记录了 LiteLLM 1.107.0 发布物遭篡改，并保留官方当时对内部日志泄露的怀疑。后续官方攻击链调查已修正这一点：一个内部 Agent 平台的管理密钥曾进入公开仓库，文件被删后密钥没有实际撤销，历史提交也仍可访问。攻击者利用它进入平台，再取得具有组织所有者权限的 GitHub 令牌，继而影响发布工作流。

这里的权限差别解释了为何一次泄露会进入发布链。该实验平台原本用来让云端 Agent 向代码仓库提出修改，因此配置了 GitHub 身份；实际使用的却是组织所有者的令牌，而非只允许必要仓库和动作的凭据。服务日常只需提交修改，不代表它持有的身份也只能提交修改。调查把这段容易被“密钥泄露”四个字略去的扩散过程补了出来。

这条新证据改变的是初始入口和权限传播路径，不是发生了第二次事故。官方称，攻击者得以绕过分支保护，把构建来源指向外观相似的仓库，最后通过正式流程发布签名产物。原先“签名不能替代构建来源核对”的判断仍成立，现在还应补上：删除泄露文件并不使旧密钥失效，Agent 服务所持权限也会决定入侵后能扩散多远。
