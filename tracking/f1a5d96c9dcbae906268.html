按时间保留当时的判断和后续核查；历史收录不代表刚刚重新验证。

2026-10-14 · 当时的记录

IBM 的芯片设计案例给旧成本问题增加了一个具体对照：相同的假设数量，得到的设计并不相同。[1] 因而“搜索更便宜”不能直接读成“买到了相同质量的结果”。对团队而言，先确定设计的速度和资源门槛，再比较满足门槛的费用，往往比先看价格倍数更有用。

值得保留的正面证据是，开放模型和服务系统一起降低了这次探索的推理账单。它不是靠少生成 token 得来的：文中开放配置反而使用了更多 token。这个细节修正了把便宜一律归因于“少做事”的阅读倾向。与此同时，模型配置、服务价格与缓存共同变化，现有比较并没有单独识别每项机制贡献多少。

如果目标是一个能用的紧凑设计，较便宜的方案可能已经够用；如果必须追求更低延迟，另一配置的额外收益也可能值得花钱。这不是用结果质量否定低成本，而是让低成本落在实际的选择上。作者增加开放搜索预算后的收益递减，也提醒我们，省下的钱不一定按比例变成更好的设计。多次独立搜索比一次继续扩展更好，还是更差，仍需比较。

Minions 则把费用问题移到资源取得方式：闲置 Mac 可以减少新增设备需求，却仍需要领取任务、保存输出和处理机器离线。[2] HN 的 dekhn 从自述的闲置算力经历提出尾延迟、异构兼容与管理问题。[3] 这不是对 Minions 的独立测试，但提供了原报告没有量化的核算对象。若已有资源只能在某些时段用，“能开始运行”与“能按期交付”就可能不同。

BranchOPD 的生成 token 节省又是第三种口径，教师评分、反向传播和环境恢复仍在这个数字之外。[4] 它与闲置设备和缓存路由没有共享实验，收益不能相加；并排阅读的意义是提醒我们，优化最先测到的那一段，未必是用户最后支付的那一段。

回访后的判断保留旧问题，但把比较条件补得更严格：不是只要求总预算一致，还要写清可接受结果的门槛。先预定一组任务、最低质量和截止时间，再核算成功及失败的推理、验证、综合、重试和人工成本；硬件探索同时报告延迟与面积，批任务报告最慢部分何时完成。若更便宜的方案只在放宽要求后达标，应如实呈现这个取舍。当前仍缺重复搜索和完整工作流账单，不能把三个案例合成普遍省钱结论。

Context Mode 的仓库把一组工具输出压到很小，当前网站又给出成对任务费用估算。[1][2] 前一个数字测量进入上下文的字节，后一个把一段任务中的模型调用计入费用。两者都可能有用，却不能互相替代。过去关注“省下的调用费会不会花在别处”，今天首先要修正一个容易延续的怀疑：不能在已读到新测量后，仍说项目只测过压缩比例。

新测量也留下具体条件。当前网关把输出处理、缓存和其他机制一起打开，并包含短回答风格；同一脚本任务反复运行，支持这个任务上的采样估计，不支持任意任务分布。文档又只展示区间完整落在省钱方向的结果。[2] 我因此把它当作值得继续检查的正面证据，而不会把节省区间写成所有用户都能达到的保证。仓库插件、商业网关和不同客户端仍要分开。

3月的外部分析追问检索往返成本，当前候选 PR 则给出一个更可操作的失败：某类非 ASCII 词边界让应有的记忆没有被召回。[3][4] 前者是方法批评，后者是作者报告的基准对照，两者都不是编辑独立复现。没有找到与找到错误信息会造成不同后果，评测不该只把它们记为一句“搜索失败”。

这使我更关注压缩的单位。对于问日志有多少错误，先写程序统计可能保留全部所需信息；对于判断一个约束是否违反，先给标题和计数可能省掉真正关键的条件。保存在外部不等于已进入模型的判断，也不等于它会想到正确检索词。应让任务预先指定需要找到的证据，记录回读次数、首次命中、误取旧约束以及最后是否完成。

SWE-TaskFlow 在同一组目标与最终测试下改变信息逐步出现的方式，费用就变了。[5] Meta 的新模型则强调跨会话记忆与持续执行。[6] 这些材料没有共同验证一种压缩方案，但让比较目标更清楚：既要看信息怎么存，也要看何时取出、任务改向后能否换掉旧判断。存储更省与使用更可靠应分别测量。

可以从几十个有明确证据位置的长任务开始，比较全文、摘要后按需检索、以及稳定前缀加按需检索三种方式。保持模型、最终测试和总预算一致，计入索引、追问与失败运行；另放一组有同名实体、旧版本约束和多语言术语的任务。若摘要方式只在简单统计题上省钱，就把适用范围收回到统计题。这样的负结果也能帮助我们决定哪些信息不应提前压掉。

Asana 的案例里，最有意思的地方不是标题中的倍数，而是一个违反直觉的结果：每轮删除旧截图、缩短历史，可能让调用更贵。原因是修改了前面的内容，后续请求不能继续复用原来的缓存前缀；改成分批清理，则能在多轮之间保留可复用的历史。[1][5] 在这套系统中，账单既与输入有多长有关，也与相邻两次输入有多少内容没变有关。

这使 Lynch 对自动模型分工的期待多了一层需要验证的条件。他不想为了简单子任务一直支付最强模型的价格，也不想自己负责拆解和切换。[2] 这个需求合理，但“把简单问题交给便宜模型”还不是完整的成本方案。接手的模型需要知道什么，前一个模型留下的结论能否检查，失败之后由谁接着做，都会改变最终账单。

2024 年的 RouteLLM 已经研究过按请求选择模型。除了省钱结果，值得留意的是它的分布变化：只用 Arena 偏好数据训练的路由器，在 MMLU 上表现接近随机路由；加入该领域的数据后才明显改善。[4] 这提示我们，判断任务难度也需要合适的经验。“这个请求看起来短”与“便宜模型能可靠完成它”之间，并没有现成的等号。

TokenRouter 讨论的是更细的 token 级路由，不能直接当作上述任务分工的实现。它把注意力放在切换后的异步执行与批处理，说明路由策略之外还有运行时调度问题。[3] 把这几份材料放在一起，我的推断是：选择模型时，除了下一步的能力和价格，还应考虑继续使用当前状态的价值。一个略贵但已有可复用上下文的选择，可能比便宜却需要重新铺垫的选择更合算；具体能否成立，要看服务的缓存规则和任务轨迹。

不过，“少切换”也不该变成新的口号。沿用当前模型可能延续一个已经错误的思路，过长历史可能干扰判断，重新整理上下文有时恰好能减少返工。真正要比较的是切换的增量收益与增量代价：它有没有提高最终完成率、减少后续尝试，代价又有多少来自重新输入、生成、排队和验证。只数调用次数，会把这些效果压成同一个数字。

我会把后续实验的核算单位定为一批原先就确定好的任务，而不是事后挑出的成功请求。分别比较固定模型、按子任务路由，以及把缓存与近期失败记录纳入决策的路由；保持验收要求和时限一致，报告整批总费用、完成率、等待时长，再给出每个合格结果分摊的费用。失败任务消耗的预算仍留在总费用里，否则最容易失败的方案反而可能显得便宜。

还需要看组合效果。可以把稳定前缀策略和模型路由分别打开、关闭，观察四种设置：两项优化是否互相促进，还是其中一项把另一项赖以成立的条件破坏了。今天的几份材料还没有回答这个组合问题。它比“多模型一定省钱”更值得追踪，也可能为路由器提供一个更实际的目标：不要只预测下一次回答的质量，要预测这一步会给后续任务留下什么成本。
