Ben Congdon：让模型写监控方案，再由固定程序执行

按时间保留当时的判断和后续核查；历史收录不代表刚刚重新验证。

2026-10-20 · 当时的记录

Ben Congdon 讨论的是线上软件发布或推送配置后的监控：一次改动进入系统后，怎样及时发现它引入的退化。他从 2023 年起就在接触这类工作，长期遇到两难。先服务运维成熟的团队，原有告警已能守住许多问题，新系统主要省去杂务；若一下覆盖所有服务，只盯少数通用健康指标，又容易把正常波动当异常，造成告警疲劳。有效监控还依赖团队标好变更、定义信号并持续维护。

他的切入点是让模型为每次变更提出具体检查办法。原型先让 Agent 阅读服务代码、理解配置怎样被使用，写出监控方案；固定执行器持续运行方案；信号触发后，再交给 Agent 查日志和相关证据，必要时升级给人处理。作者试过纯 Agent 循环，认为“模型写规格、程序执行规格”能得到更干净的信号，并减少 token 消耗；降噪规则、提示和有标注的评估集仍需专门建设。

Congdon 乐观的理由，是模型能够长时间重复查询，并沿几条可能原因并行调查，覆盖人无暇逐一查看的变化。他也承认，读得更快不总能更快发现问题：熟悉系统的工程师可能凭经验直接找到关键信号。文章主要是原型经验与设计判断，自动回滚、修复和更广部署仍属于后续设想。下方保留作者及读者的具体论述，其中大型系统的资料关联困难，是对扩大覆盖范围的实质追问。
