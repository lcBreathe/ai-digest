Simon 做出了想玩的游戏，也碰到自动测试没听见的噪声

Simon Willison 用编码 Agent 做了一款浏览器即时战略游戏 Battle Drones。到这篇文章发布时，项目经历12次主要迭代、321次提交；他自述几乎没审查代码，但做了大量试玩。最初的版本只是看起来像游戏，并不好玩。后来他让 Agent 改进趣味性、进行自动对局，再由自己继续判断规则和体验。

一个具体改变很能说明人的作用：运输机虽然已经存在，却没有使用理由。Simon 加入必须由步兵占领、又需要空运才能到达的岛屿，让地形、兵种和目标形成关系。这里的新能力，是一个人可以把原本很难完成的游戏想法变成可反复试玩的作品；“有功能”到“有意义”的跨越仍来自设计判断。

最奇特的实验是用声音传输双人对战数据，减少对服务器的依赖。确定性模拟也遇到浏览器间细小三角函数差异，作者让 Agent 做了兼容处理。不过，文章后续更新给了更直接的使用反馈：他与 Natalie 实际游玩时，高频音让人头痛。作者添加警告，尝试 WebRTC，在自己的 Wi-Fi 下失败后又做了无状态 WebSocket 中继，使在线联机成为替代方案。

这是一份公开的个人创作经历，不是对代码安全、游戏平衡或模型能力的完整评测。自动对局可以帮助寻找拖延和失衡，却没有替他发现真人听到声音后的感受。

编辑评读

这个案例令人兴奋的地方是试作成本下降：即使不会从零实现完整游戏引擎，作者也能围绕自己的兴趣不断修改一个可玩的作品。具体的运输机改动尤其值得保留，它表明有效反馈不总是更细的实现指令；有时只需指出玩家没有理由做某个动作，再修改激励关系，就能改变玩法。

音频联机的转折则提示，测试要跟随使用场景。模拟玩家可以度量对局，却没有耳朵，不能替真人判断持续高频声是否可接受。发现问题后，作者改变传输方式，意味着“不用服务器”的原始目标需要让位于可玩的体验。可迁移的方法是先说清每种测试能感知什么，再给剩余部分安排真实使用；本期只阅读文章及公开更新，未试玩、未验证联机效果，也不把他自述的趣味性当作普遍玩家评价。
