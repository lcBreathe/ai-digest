Datasette Apps：把可调用的数据能力限定到每个应用

原始来源：README 与查询桥说明

Datasette 用来浏览和查询结构化数据。它的 Apps 插件让用户把 HTML、JavaScript 小应用放在同一系统内，例如为一份数据库做专用界面，再让 Agent 帮忙修改。困难是：生成页面能够运行，不代表它就该拿到整个站点的数据与写权限。0.3a0 的更新把应用编辑、查询和聊天里的引用连接得更完整。

仓库说明，HTML 应用运行在隔离的 iframe 中——它像页面内一个受限制的小窗口。默认不能随意向外联网，外部地址需要明确允许。应用需要查询数据时，通过消息桥把请求交给父页面，再送到应用专属的查询端点；请求同时受当前用户原有权限和该应用允许范围约束。预先保存的查询还可以承载明确的动作，而不是给每个生成页面一把任意操作数据库的钥匙。

这一版本在聊天中加入应用标签补全，只显示当前用户可见的应用；Agent 可以创建应用、添加或移除已保存查询。创建时检查查询是否存在及用户能否查看，授予应用可调用写查询的权限仍需要用户批准。把应用加入聊天时传递的是标识、链接和编辑权限，完整 HTML 不会随标签自动送入上下文；读取源码还有相应的权限要求。每次编辑保留版本，方便查看改动。

这些是插件和版本说明中可以核对的实现安排，还不是对所有攻击情境的安全证明。仓库另有权限更大的 Python 插件应用，不能把 HTML 应用的隔离承诺推广到所有应用类型。对开发者来说，这个例子的价值是把“展示一个界面”和“授予它一项操作能力”分别设计，再在需要协作时显式连接。

编辑评读

常见的做法是让 Agent 先获得数据库访问权，再靠提示要求它只查某些表。Datasette Apps 把另一部分约束放进应用接口：用户、应用、具体查询各有可说明的范围。这样做的收益不是让模型多记住一条规则，而是把不属于这个小应用的操作，从它通常能请求的范围里移出去。

同时，约束不能只剩禁止。应用标签提供可发现的入口，工具返回可用链接，保存查询给出明确动作，版本记录留下编辑结果。这些安排让用户可以继续让 Agent 做事，而不必在“全部授权”与“每步手动执行”之间选一边。这里有一种可迁移的产品方法：先辨认用户真正需要授出的能力单位，再把它做成可见、可撤回、能说明后果的操作。

仍需留意的是，范围清楚不自动等于操作正确。即便一次写入完全合法，也可能填错行、误解用户意图。下一层验证应面向具体任务的结果和回退方式，而不是把查询端点的权限检查当成全部质量保证。学习卡给出一个使用自建小数据库的练习，用来理解这个分工；本期没有运行插件或做安全测试。
